> 목적: 모델·버전에 비교적 독립적인 프롬프트 설계 원리와 기법을 제공하는 공통 지식 문서

> 원칙: 모든 기법을 넣는 것이 아니라, 작업에 필요한 최소 충분 구조를 선택한다.

## 1. 프롬프트 설계의 기본 철학

프롬프트는 명령의 나열이 아니라 **목표·맥락·제약·평가기준·출력 조건을 설계하는 작업 인터페이스**다.

최신 추론 모델일수록 모델에게 세부 사고 절차를 과도하게 강제하기보다 다음을 명확하게 제공하는 것이 중요하다.

1. 무엇을 달성해야 하는가
2. 어떤 맥락에서 수행하는가
3. 무엇을 지켜야 하는가
4. 좋은 결과의 기준은 무엇인가
5. 어떤 형태로 결과를 제공해야 하는가

핵심 원칙은 **최소 충분 구조(Minimum Sufficient Structure)**다.

- 단순한 작업은 짧고 직접적으로 설계
- 복잡한 작업만 필요한 수준으로 구조화
- 같은 지시를 여러 표현으로 반복하지 않음
- 모델 자체 추론 능력과 중복되는 메타 지시를 줄임
- 좋은 프롬프트의 기준을 길이가 아니라 과업 성능으로 판단

## 2. 기본 Prompt Architecture

### 2.1 Core 5

대부분의 Chat 작업은 다음 다섯 요소를 중심으로 설계한다.

### Goal
최종적으로 달성해야 할 결과.

좋은 Goal은 행동보다 **결과 상태**를 명확히 한다.

예:
- 나쁨: 시장을 조사해줘.
- 좋음: 국내 중소기업이 향후 12개월 안에 도입할 수 있는 AI Agent 사업 기회 5가지를 도출한다.

### Context
결과 판단에 필요한 배경·대상·사용 목적·전제.

포함 가능한 정보:
- 목표 독자
- 산업·업무 맥락
- 사용 목적
- 기존 결정사항
- 참고자료의 성격
- 시간적·지역적 범위

### Constraints
반드시 지켜야 할 조건과 제외 범위.

예:
- 2026년 자료 우선
- 실제 상용 사례만 포함
- 2,000자 이내
- 특정 기술 제외
- 제공 자료에 없는 사실 임의 생성 금지

제약은 많을수록 좋은 것이 아니다. 결과에 실질적으로 영향을 주는 조건만 사용한다.

### Success Criteria
좋은 결과라고 판단할 기준.

예:
- 정확성
- 최신성
- 신뢰성
- 실행 가능성
- 비교 가능성
- 논리적 일관성
- 대상 독자 적합성

가능하면 추상적 형용사보다 **판단 가능한 기준**으로 작성한다.

예:
- "전문적으로 작성"보다
- "핵심 주장마다 근거를 제시하고, 실행안에는 예상 난이도와 선행조건을 포함"

### Output
최종 결과의 형식·구조·분량·문체.

예:
- 1,500자 이내
- Executive Summary → 비교표 → 권고안
- 개조식
- Markdown
- 초보자도 이해할 수 있는 용어 수준

## 3. 선택적 Prompt Blocks

Core 5만으로 부족할 때 다음 요소를 선택적으로 추가한다.

### Role
특정 전문 관점이 결과 품질에 실제 도움이 될 때 사용.

예:
- 투자자 관점
- 교육설계 전문가 관점
- UX 리서처 관점

단순히 "세계 최고 전문가"와 같은 과도한 역할 수식은 핵심 설계 요소로 간주하지 않는다.

### Input
분석할 데이터·문서·예시·참고자료의 범위와 사용 방법을 명시.

### Task
수행해야 하는 핵심 과업.

Goal이 "도착점"이라면 Task는 "해야 할 일"이다.
단순 작업에서는 Goal과 합칠 수 있다.

### Process
특정 순서가 품질·안전·재현성에 필요할 때만 사용한다.

예:
자료 수집 → 검증 → 유형화 → 비교 → 시사점 도출

모델에게 상세한 내부 사고과정을 출력하도록 요구하지 않는다.

### Evidence
사실·수치·시장정보·법규 등 검증 가능한 주장에 필요한 근거 수준을 지정한다.

예:
- 공식 문서 우선
- 1차 출처 우선
- 주요 수치에 출처 표시
- 사실과 추론을 구분

### Verification
오류 비용이 높거나 최신성·사실성이 중요한 작업에서 검증 규칙을 지정한다.

### Examples
형식·톤·판단기준이 말로 설명하기 어려울 때 Few-shot 예시를 사용한다.
예시는 적을수록 좋다는 뜻이 아니라, **정보가치가 있는 예시만 사용**한다.

## 4. 프롬프트 설계의 3계층

### Level 1. Core Prompt
기본 구조.

- Goal
- Context
- Constraints
- Success Criteria
- Output

### Level 2. Quality / Reasoning
품질과 검증 요구가 높을 때 선택적으로 추가.

- Role
- Input
- Process
- Evidence
- Verification
- Evaluation
- Few-shot

### Level 3. Agent Operation
AI가 여러 단계의 작업을 직접 수행하는 환경에서만 추가.

- Autonomy
- Clarification Rule
- Approval Boundary
- Verification
- Completion Criteria
- Delegation

Agent Operation의 상세 원칙은 별도 최신 모델 가이드의 Work 섹션을 우선 참고한다.

## 5. 작업 난이도 스케일링

### Low
특징:
- 단일 목적
- 낮은 오류 비용
- 단순 생성·요약·변환

설계:
- Goal + Context + Output
- 필요한 경우 Constraints만 추가

### Medium
특징:
- 분석·비교
- 여러 조건
- 판단기준 필요
- 어느 정도의 사실 검증 필요

설계:
- Core 5
- 필요한 경우 Task / Evidence / Verification 추가

### High
특징:
- 전략·의사결정
- 높은 오류 비용
- 최신 정보 필요
- 여러 관점 충돌
- 복합 자료 분석

설계:
- Core 5
- Evidence / Verification 강화
- 필요한 경우 Task Decomposition, Rubric, Scenario Exploration 등 선택
- 모든 고급 기법을 자동 적용하지 않음

## 6. 고급 프롬프트 기법

### 6.1 Prompt Optimization / OPRO

정의:
AI를 활용하여 프롬프트 구조·문구·평가기준을 개선하는 접근.

적합:
- 반복 사용되는 프롬프트
- 결과 품질 평가기준이 명확한 작업
- 여러 버전을 비교할 수 있는 경우

주의:
- 모든 단발성 작업에 별도의 최적화 루프를 만들 필요 없음
- OPRO는 상위 철학이 아니라 여러 최적화 기법 중 하나로 취급

### 6.2 Task Decomposition

복잡한 작업을 의미 있는 하위 과업으로 나누는 기법.

적합:
- 서로 다른 분석 단계가 존재
- 중간 산출물이 최종 품질에 중요
- 단계별 검증이 필요

주의:
모델의 내부 사고과정을 장황하게 출력시키는 것과 구분한다.

### 6.3 Verification Strategy

사실 오류·누락·모순을 줄이기 위해 초안과 검증을 분리하는 접근.

가능한 방식:
- 핵심 주장 재검증
- 독립적 출처 확인
- 조건 충족 체크
- 반례 탐색
- 계산 재확인

### 6.4 CoVe

초안 → 검증 질문 → 독립 확인 → 수정의 흐름을 사용하는 검증 기법.

적합:
- 사실성 중심 작업
- 여러 주장·수치가 포함된 결과

주의:
특정 정확도나 신뢰도를 보장하는 기법으로 표현하지 않는다.

### 6.5 Multi-Perspective

하나의 모델이 서로 다른 관점에서 문제를 검토하게 하는 방법.

예:
- 고객
- 경영자
- 투자자
- 규제자

이는 실제 여러 Agent를 실행하는 Subagent Delegation과 구분한다.

### 6.6 Red Team

초안·전략·주장의 취약점, 반례, 실패 조건을 찾는 기법.

적합:
- 전략
- 의사결정
- 정책
- 리스크 분석

### 6.7 Evaluation Rubric

좋은 결과의 판단기준을 루브릭으로 명시하는 방법.

예:
- 정확성 30
- 실행가능성 30
- 차별성 20
- 명료성 20

단순 작업에 불필요하게 복잡한 루브릭을 만들지 않는다.

### 6.8 Review & Revision

최종 결과가 목표·제약·성공기준을 만족하는지 점검하고 필요한 부분만 수정.

"무조건 여러 번 자기비판"보다 실제 오류 가능성과 작업 중요도에 맞춘 품질 점검을 선호한다.

### 6.9 Scenario Exploration

불확실성이 큰 전략 문제에서 단일 답 대신 복수 시나리오를 탐색.

예:
- 낙관
- 기준
- 보수

## 7. 질문 설계

AI가 사용자에게 질문하는 목적은 정보 수집 자체가 아니라 **결과 품질을 크게 바꿀 핵심 불확실성 제거**다.

질문이 필요한 경우:
- 목표가 서로 다른 두 방향으로 해석 가능
- 대상 독자에 따라 결과 구조가 크게 달라짐
- 사용할 AI 환경·기능이 설계를 실질적으로 바꿈
- 중요한 제약 또는 평가기준이 결정되지 않음

질문하지 않아도 되는 경우:
- 대화 맥락에서 합리적으로 추론 가능
- 사소한 형식·표현 선택
- 사용자가 "알아서 최적화"를 요청
- 질문 비용이 얻는 정보가치보다 큼

질문은 가능한 한 1~4개 핵심 질문으로 제한하고, 필요하면 선택지를 제공한다.

## 8. 컨텍스트 엔지니어링

좋은 결과는 프롬프트 문장만이 아니라 모델이 실제로 받는 전체 컨텍스트의 품질에 좌우된다.

### 구조화
목표·배경·제약·자료·출력 조건을 서로 구분한다.

### 관련성
"도움이 될 수도 있는 정보"를 모두 넣지 않는다.
현재 과업에 필요한 정보만 유지한다.

### 정보 배치
안정적인 핵심 지침은 명확하게 구조화한다.
긴 참고자료가 있다면 자료와 수행 지시를 구분하고, 필요 시 자료 뒤에 최종 과업을 명확히 제시한다.

### 맥락 증류
긴 대화나 많은 자료에서는 다음을 중심으로 압축한다.

- 확정 사실
- 주요 결정
- 핵심 제약
- 미해결 이슈
- 현재 목표

### 지시 충돌
여러 문서·규칙·예시가 존재할 경우 서로 충돌하는 내용을 줄인다.
같은 규칙을 여러 곳에서 조금씩 다르게 반복하지 않는다.

## 9. 작업 유형별 설계

### 사실·리서치
중점:
- 최신성
- 출처
- 사실/추론 구분
- 불확실성 표시
- 중요 주장 검증

권장 흐름:
질문 정의 → 자료 탐색 → 신뢰도 평가 → 비교·종합 → 결론

### 분석·전략
중점:
- 의사결정 기준
- 원인·패턴
- 대안 비교
- 리스크
- 실행안

권장 흐름:
현황 → 패턴/원인 → 의미 → 선택지 → 권고 → 실행조건

### 창의적 작업
중점:
- 과도한 제약 회피
- 다양성 확보
- 평가기준과 생성 단계 분리

필요 시:
아이디어 확장 → 후보 압축 → 평가 → 추천

### 장문 자료
중점:
- 자료와 지시 분리
- 핵심 범위 지정
- 정보 누락보다 관련성 우선
- 필요 시 중간 요약 또는 맥락 증류

---

## 10. 출력 설계

출력 형식은 결과 품질에 직접 영향을 준다.

좋은 Output 지시는 다음을 구체화한다.

- 구조
- 분량
- 문체
- 대상 독자 수준
- 표·목록 사용 여부
- 반드시 포함할 항목
- 제외할 항목

"전문적으로", "깔끔하게" 같은 추상적 표현만 사용하는 것보다 실제 작성 행동을 정의한다.

예:
- 핵심 결론을 먼저 제시
- 전문용어는 첫 사용 시 설명
- 동일 내용 반복 금지
- 표는 비교가 필요한 경우에만 사용

---

## 11. 피해야 할 프롬프팅 패턴

- 같은 규칙을 여러 번 반복
- 모든 작업에 긴 Role 적용
- 모든 고급기법 자동 적용
- 상세한 Chain-of-Thought 출력 강제
- 단순 작업에 복잡한 단계 강제
- 불필요한 Few-shot 예시 다수 삽입
- "더 깊이 생각해라" 같은 모호한 메타 지시 남용
- 사용자에게 이미 제공된 정보를 다시 질문
- 모델 기능을 확인하지 않고 단정
- 고정 글자 수·페이지 수를 토큰 수로 단순 환산
- 특정 프롬프트 기법이 일정 정확도를 보장한다고 표현

---

## 12. 프롬프트 품질 체크리스트

최종 프롬프트를 다음 기준으로 점검한다.

1. Goal이 결과 중심으로 명확한가?
2. 필요한 Context가 충분한가?
3. Constraints가 중요 조건만 포함하는가?
4. Success Criteria가 판단 가능하게 정의되었는가?
5. Output이 실제 사용 목적에 맞는가?
6. 같은 지시가 반복되지 않는가?
7. 상세 CoT를 불필요하게 요구하지 않는가?
8. 고급 기법이 실제 품질 향상에 필요한가?
9. 질문해야 할 핵심 모호성이 남아 있는가?
10. 더 짧게 해도 같은 성능을 유지할 수 있는가?

---

## 13. 최신 모델 대응 원칙

모델명·기능·검색·도구·추론 옵션은 빠르게 변경된다.

따라서:
- 특정 모델 특성이 프롬프트 설계에 중요한 경우 최신 공식 문서를 우선
- 모델별 세부 프롬프팅 원칙은 별도의 최신 모델 가이드를 참고
- 검증되지 않은 기능·파라미터를 단정하지 않음
- 모델 자체 추론 기능이 충분한 경우 불필요한 사고 절차를 추가하지 않음

이 문서는 모델별 세부 사양보다 **장기간 유지되는 프롬프트 설계 원칙**을 담당한다.
